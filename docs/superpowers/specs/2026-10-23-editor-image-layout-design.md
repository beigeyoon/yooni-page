# 에디터 이미지 레이아웃 배치와 업로드 전 압축 설계

작성일: 2026-10-23
대상: yooni-page 에디터 (`src/components/TiptapEditor`)

## 배경

에디터의 이미지 업로드에 두 가지 불편이 있다.

1. 여러 장을 고르면 선택한 순서대로 묶음 하나에 들어가고, 배치는 장수(`data-count`)로만 정해진다.
   같은 3장이라도 "큰 1장 + 작은 2장" 같은 배치를 고를 수 없고, 순서를 바꾸려면 파일을 다시 골라야 한다.
2. 큰 사진은 업로드가 거부된다.

## 현재 상태

### 업로드 흐름

`Toolbar.tsx`의 숨은 `<input type="file" multiple>`이 파일을 받아
HEIC면 `heic2any`로 JPEG 변환한 뒤 `uploadImage`로 한 장씩 순차 업로드하고,
성공한 URL들을 `imageGroup` 노드 하나로 삽입한다.

`ImageGroup`(`src/extensions/ImageGroup.ts`)은
`<div class="image-album" data-count="N" style="--count: N;">`로 렌더된다.
배치는 `globals.css`가 `data-count`별 grid로 정하고, 칸은 모두 정방형(`aspect-ratio: 1/1`)이다.
640px 이하에서는 세로로 풀어 원본 비율로 보여준다.

### 업로드 거부 원인

`/api/upload`는 10MB까지 받도록 되어 있지만 **Vercel 서버리스 함수의 요청 본문 한도는 4.5MB**다.
그보다 큰 요청은 라우트 코드가 실행되기 전에 Vercel이 413으로 거부한다.
이 응답은 JSON이 아니어서 `uploadImage`의 `res.json()`이 예외를 던지고, 사용자에게 원인이 보이지 않는다.

2026-08-07 실측 기준 원본 사진은 평균 2.96MB, 최대 13.67MB(아이폰 3024×4032)다.

### 상세 페이지 경로

상세 페이지는 `optimizePostHtml(sanitizePostHtml(post.content))`로 본문을 렌더한다.
`sanitizePostHtml`은 `div`에 `class`, `data-count`, `style`만 허용한다.
`.image-album` 스타일은 `globals.css`에 있어 에디터(`.editor-container`)와 상세(`.post-content`)가 공유한다.
상세에는 `.post-content img { height: auto; }`가 있다.

## 목표

1. 장수(1~4)와 레이아웃을 먼저 고르고, 각 칸에 맥 파인더에서 사진을 끌어다 놓아 배치한다.
2. 업로드 전에 브라우저에서 사진을 줄여 4.5MB 한도에 걸리지 않게 한다.
3. 기존 글의 사진 묶음은 지금 모습 그대로 유지한다.

## 결정 사항

| 항목 | 결정 |
| --- | --- |
| 묶음당 장수 | 1~4장. 5장 이상은 묶음을 여러 번 넣어 조합한다 |
| 레이아웃 | 1장 1개, 2장 3개, 3장 5개, 4장 6개 (총 16개) |
| 칸 비율 | 정방형 1:1, 가로형 4:3, 세로형 3:4. 예외로 섞인 레이아웃의 큰 사진과 세로·가로가 나란한 칸은 세로 2:3, 가로 3:2로 두어 형태를 분명히 한다(3-c, 3-d, 3-e, 4-c, 4-d). 넘치는 부분은 잘라 채운다(`object-fit: cover`) |
| 1장 | 원본 비율 그대로, 자르지 않는다 |
| 사진 출처 | 맥 파인더에서 칸으로 직접 드롭, 또는 칸 클릭으로 파일 선택. 별도 대기 영역 없음 |
| 칸 배정 | 가로·세로 사진은 사용자가 맞는 칸에 직접 넣는다. 자동 배정하지 않는다 |
| 기존 묶음 수정 | 지원하지 않는다. 지우고 다시 넣는다 |
| 모바일(≤640px) | 지금처럼 세로로 풀어 원본 비율로 보여준다 |
| 압축 | 긴 변 2048px, WebP 품질 0.82. WebP 인코딩이 안 되면 JPEG 0.85 |
| 드래그 앤 드롭 | 브라우저 기본 HTML5 DnD. 새 라이브러리 없음 |
| 압축 구현 | canvas로 직접 작성. 새 라이브러리 없음 |
| 레이아웃 저장 | `data-layout` 속성 + CSS. inline style로 배치를 박지 않는다 |

## 레이아웃 목록

칸 표기: **정** 정방형 1:1, **가** 가로형 4:3, **세** 세로형 3:4. 숫자는 배치 순서다.

 │ 정1 │ 정2 │        │     │     │        │    가1    │

                      │     │     │        │    가2    │
                      └─────┴─────┘        └───────────┘
3장
 3-a 정방형 3열        3-b 세로형 3열        3-c 세로1 + 가로2
 ┌───┬───┬───┐        ┌───┬───┬───┐        ┌──────┬─────┐
 │정1│정2│정3│        │   │   │   │        │      │ 가2 │

 │ 가1 │      │        │    가1    │
 ├─────┤ 세3  │        ├─────┬─────┤
 │ 가2 │      │        │ 정2 │ 정3 │
 └─────┴──────┘        └─────┴─────┘
4장
 4-a 정방형 2×2        4-f 가로형 2×2        4-b 정방형 4열
 ┌─────┬─────┐        ┌──────┬──────┐      ┌──┬──┬──┬──┐
 │ 정1 │ 정2 │        │ 가1  │ 가2  │      │정│정│정│정│

 └─────┴─────┘        └──────┴──────┘

 ┌───────────┐                ┌───────┬───┐        ┌──┬──┬──┬──┐
 │   가1     │                │       │가2│        │  │  │  │  │
 │  (3:2)    │                │  세1  ├───┤        │세│세│세│세│
 ├───┬───┬───┤                │ (2:3) │가3│        │  │  │  │  │
 │정2│정3│정4│                │       ├───┤        └──┴──┴──┴──┘

                              └───────┴───┘

혼합 레이아웃(3-c, 3-d, 4-d)은 양쪽 열의 높이가 같아지도록 열 폭 비율을 정한다.
세로 칸은 2:3, 가로 칸은 3:2다. 3-c에서 왼쪽 폭을 a, 오른쪽 폭을 b라 하면
`3/2·a = 2·(2/3)·b`이므로 `a : b = 8 : 9`다. 4-d는 `3/2·a = 3·(2/3)·b`, 즉 `4 : 3`이다.
3-e와 4-c는 위 사진을 3:2로 두고 아래는 정방형이다.
gap 때문에 칸 비율이 정확히 4:3이 되지는 않지만 `object-fit: cover`가 차이를 흡수한다.

## 설계

### 1. 압축 — `src/utils/compressImage.ts` (신규)

```
compressImage(file: File): Promise<File>
getTargetSize(width, height, maxEdge = 2048): { width, height }   // 순수 함수
```

처리 순서:

1. GIF·SVG는 그대로 반환한다. 재인코딩하면 애니메이션과 벡터가 깨진다.
2. `createImageBitmap(file)`로 디코딩한다. EXIF 회전은 기본값(`imageOrientation: 'from-image'`)으로 반영된다.
   실패하고 HEIC면(`type === 'image/heic'` 또는 확장자 `.heic`) `heic2any`로 JPEG 변환 후 다시 디코딩한다.
   Safari는 HEIC를 직접 디코딩하므로 변환을 건너뛴다.
3. `getTargetSize`로 긴 변을 2048px 이하로 줄인다. 확대하지 않는다.
4. canvas에 그려 `toBlob('image/webp', 0.82)`로 인코딩한다.
   **Safari는 WebP 인코딩을 지원하지 않으면 조용히 PNG를 돌려준다.** 결과 `blob.type`이 `image/webp`가 아니면
   `toBlob('image/jpeg', 0.85)`로 다시 인코딩한다.
5. 확장자를 결과 타입에 맞춰 바꾼 `File`을 반환한다.

재인코딩 과정에서 EXIF 전체(GPS 포함)가 제거된다. 여행 사진이 많아 개인정보 측면에서도 이득이다.

`uploadImage`가 내부에서 `compressImage`를 호출한다. 업로드 경로가 늘어나도 압축을 빠뜨리지 않게 하기 위해서다.
`Toolbar.tsx`의 HEIC 변환 코드는 이 파일로 옮기고 제거한다.

### 2. 업로드 에러 처리 — `uploadImage.ts`, `/api/upload`

- `uploadImage`는 응답이 JSON이 아니어도 실패를 처리한다. 413이면 "용량 초과" 메시지를 돌려준다.
  지금처럼 `null`만 돌려주면 배치 창이 실패 사유를 보여줄 수 없으므로,
  반환형을 `{ url } | { error }` 형태로 바꾼다. 호출부는 툴바 한 곳뿐이고 이번에 배치 창으로 대체된다.
- `/api/upload`의 `MAX_FILE_SIZE`를 10MB에서 4MB로 낮춘다.
  Vercel 실제 한도(4.5MB) 아래로 맞춰, 거부될 때 우리 쪽 메시지가 나오게 한다.

### 3. 레이아웃 목록 — `src/utils/imageLayouts.ts` (신규)

```ts
type CellRatio = 'square' | 'landscape' | 'portrait' | 'original';
type ImageLayout = { id: string; count: 1 | 2 | 3 | 4; label: string; cells: CellRatio[] };
export const IMAGE_LAYOUTS: ImageLayout[];
export function getLayoutsByCount(count): ImageLayout[];
export function getLayout(id): ImageLayout | undefined;
```

배치 창(썸네일, 칸 비율 표시)과 테스트가 이 목록을 공유한다.
실제 칸 배치는 CSS가 담당하므로 grid 정보는 여기에 두지 않는다.
목록과 CSS가 어긋나지 않도록 테스트에서 `globals.css`에 모든 id의 셀렉터가 있는지 확인한다.

### 4. 배치 창 — `src/components/ImageLayoutDialog/` (신규)

툴바의 이미지 버튼이 기존 파일 선택 대신 이 창(Radix Dialog)을 연다.

흐름: **장수 선택(1~4) → 레이아웃 썸네일 선택 → 빈 칸에 사진 놓기 → [삽입]**

칸 동작:

- 파인더에서 파일을 드롭하면 `dataTransfer.files`에서 이미지 파일만 받는다.
  여러 장을 한 칸에 놓으면 그 칸과 이후의 빈 칸에 순서대로 채우고, 남는 파일은 버린다.
- 칸을 클릭하면 파일 선택 창이 열린다.
- 사진이 든 칸은 드래그해서 다른 칸과 자리를 바꿀 수 있다.
  칸 간 이동은 커스텀 타입(`application/x-image-slot`)으로 구분해 파인더 드롭과 섞이지 않게 한다.
- 각 칸에 미리보기(`URL.createObjectURL`)를 보여준다. 창을 닫거나 사진을 바꾸면 URL을 해제한다.

상태 유지:

- 같은 장수 안에서 레이아웃을 바꾸면 사진은 순서대로 유지된다.
- 장수를 바꾸면 앞에서부터 새 칸 수만큼 유지하고 넘치는 사진은 뺀다.

삽입:

- 모든 칸이 차야 [삽입]이 활성화된다.
- [삽입] 시점에 압축과 업로드를 병렬로 진행하고 칸마다 진행 상태를 표시한다.
- 실패한 칸에 사유를 표시하고 창은 열어둔다. 재시도하면 성공한 칸의 URL은 재사용하고 실패한 칸만 다시 올린다.
- 모두 성공하면 `imageGroup` 노드를 `layout` 속성과 함께 삽입하고 창을 닫는다.

창 안의 미리보기도 같은 `.image-album[data-layout]` CSS를 써서 본문과 모양을 일치시킨다.

### 5. 저장 구조 — `ImageGroup` 확장

`layout` 속성을 추가한다.

```html
<div class="image-album" data-count="3" data-layout="3-c" style="--count: 3;">…</div>
```

- `parseHTML`에서 `data-layout`을 읽고, 없으면 `null`이다. `null`이면 속성을 렌더하지 않는다.
- 기존 글은 `data-layout`이 없으므로 지금 CSS 그대로 보인다.

### 6. 상세 페이지

- `sanitizePostHtml`의 `div` 허용 속성에 `data-layout`을 추가한다.
  **빠뜨리면 에디터에서는 정상인데 상세 페이지에서만 레이아웃이 사라진다.** 테스트로 고정한다.
- `globals.css`에 레이아웃 CSS를 추가한다.
  - `.image-album[data-layout]`에만 grid(`grid-template-areas`/`columns`)를 적용한다. 기존 `data-count` 규칙과 분리한다.
  - 칸 안의 `img`는 `width: 100%; height: 100%; object-fit: cover;`.
    `.post-content img { height: auto; }`보다 우선하도록 셀렉터 우선순위를 높인다.
  - 칸 비율은 각 칸의 `aspect-ratio`로 정하고, 혼합 레이아웃은 위에서 계산한 열 폭 비율을 쓴다.
  - `1-a`는 `height: auto`로 원본 비율을 유지한다.
  - `[data-layout]` 묶음끼리 바로 붙어 있으면(`.image-album[data-layout] + .image-album[data-layout]`)
    위아래 여백을 사진 사이 간격과 같게 줄여 하나처럼 보이게 한다. 기존 묶음에는 적용하지 않는다.
  - 640px 이하에서는 기존 미디어 쿼리처럼 세로로 풀고, 새로 추가한 `height: 100%`, `aspect-ratio`, grid 배치를 해제한다.

`optimizePostHtml`의 `sizes`는 칸 폭과 무관하게 780px 기준이다. 작은 칸에서 과다 다운로드가 생기지만
2026-08-07 설계와 같은 이유로 이번 범위에서 다루지 않는다.

## 에러 처리

| 상황 | 처리 |
| --- | --- |
| 이미지가 아닌 파일 드롭 | 무시하고 칸을 비워둔다 |
| 디코딩 실패(손상 파일, HEIC 변환 실패) | 해당 칸에 "이미지를 읽을 수 없음" 표시 |
| 압축 후에도 4MB 초과 | 업로드하지 않고 칸에 "용량 초과" 표시 (2048px WebP에서는 사실상 발생하지 않음) |
| 413 또는 API 에러 | 칸에 사유 표시, 재시도 가능 |
| 업로드 도중 창 닫기 | 진행 중이면 닫기 버튼을 비활성화한다 |

## 검증

| 항목 | 방법 |
| --- | --- |
| 크기 계산 | `getTargetSize` 단위 테스트 (가로·세로·작은 이미지·정사각) |
| WebP 대체 | canvas `toBlob`을 mock해 PNG를 돌려줄 때 JPEG로 재인코딩하는지 테스트 |
| GIF·SVG 통과 | 재인코딩 없이 원본을 반환하는지 테스트 |
| 레이아웃 목록 | id 중복 없음, `cells.length === count`, 장수별 개수(1/3/5/5), CSS에 셀렉터 존재 |
| 저장 구조 | `ImageGroup`이 `data-layout`을 읽고 쓰는지, 없을 때 렌더하지 않는지 |
| sanitizer | `data-layout`이 남는지 |
| 배치 창 | 드롭으로 칸 채우기, 여러 장 드롭, 칸 자리 바꾸기, 레이아웃·장수 변경 시 유지 (jsdom) |
| 실제 동작 | 로컬 브라우저에서 파인더 드래그, 큰 HEIC·JPEG 업로드, 에디터와 상세 페이지의 모양 일치, 모바일 폭 |

## 리스크

- **1-a는 종횡비가 고정되지 않아 CLS가 생길 수 있다.** 지금의 `data-count='1'` 규칙과 같은 조건이고,
  모바일에서는 이미 모든 묶음이 원본 비율로 풀리는데 실측 CLS가 0.004 이하였다. 별도 조치하지 않는다.
- 압축 품질 0.82는 추정값이다. 구현 후 실제 사진 몇 장으로 용량과 화질을 확인해 조정한다.
