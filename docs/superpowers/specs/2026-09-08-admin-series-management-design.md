# 관리자 시리즈 관리 설계

작성일: 2026-09-08
대상: yooni-page (https://yooni.seoul.kr)

## 배경

시리즈 API(`/api/series`의 GET·POST·PUT·DELETE)는 이미 관리자 권한으로 동작한다.
그런데 화면은 반쪽이다.

- 만들기·수정은 에디터의 시리즈 선택 드롭다운 안에 있는 `SeriesModal`로만 할 수 있다.
- 삭제할 수 있는 화면이 없다.
- 시리즈에 어떤 글이 들어 있는지 한눈에 볼 곳이 없다.
- 글의 시리즈 소속과 순번(`seriesOrder`)은 글마다 에디터를 열어 하나씩 고쳐야 한다.

그 결과 순번이 거의 비어 있다. 시리즈 5개 중 4개는 순번이 하나도 없고,
Fetch Diff만 3편 중 2편에 순번이 있다. 공개 시리즈 페이지는
"순번 오름차순, 순번 없는 글은 뒤로 밀고 게시일 오름차순"으로 정렬하므로,
순번이 빠진 글이 엉뚱한 자리에 놓인다.

## 현재 상태

- `/admin`은 탭이 "비공개 글 관리" 하나뿐이고, 항상 강조 스타일로 그려진다.
- 관리자 화면은 클라이언트에서 세션을 보고 관리자가 아니면 홈으로 보내는 방식이다
  (`AdminPostsManager` 안에 게이트 로직이 박혀 있다).
- 관리자 화면은 `GET /api/posts?preview=true`로 초안을 포함한 전체 글(63건)을 받는다.
  쿼리 키는 `['posts', 'preview', 'all']`이다.
- 글 수정 API(`PUT /api/posts`)는 제목·본문·카테고리를 전부 요구한다.
  소속·순번만 바꾸는 용도로 쓰기엔 무겁고, 본문을 덮어쓸 위험이 있다.
- `post.seriesId` 외래키는 `ON DELETE SET NULL`이다.
- Prisma 클라이언트는 comments·thoughts 라우트에서 이미 쓰고 있다. 트랜잭션이 필요한 곳에 쓸 수 있다.

### DB 권한 (2026-09-08 확인)

`series` 테이블에 `service_role`의 권한이 INSERT뿐이어서 시리즈 수정(PUT)과 삭제(DELETE)가
`42501 permission denied for table series`로 실패했다. 이 기능과 무관하게 원래 그랬고, 생성만 써서 드러나지 않았다.
`post`와 같게 맞췄다. `service_role`은 `BYPASSRLS`라 정책은 따로 필요 없다.

```sql
GRANT UPDATE, DELETE ON TABLE public.series TO service_role;
```

## 목표

1. 관리자 화면에서 시리즈를 만들고, 고치고, 지운다.
2. 시리즈 상세에서 소속 글의 순서와 소속 여부를 한 화면에서 편집하고 한 번에 저장한다.
3. 같은 카테고리의 다른 글(초안 포함)을 시리즈에 넣는다.
4. 저장하면 공개 페이지(홈·카테고리·시리즈·글)에 즉시 반영된다.

## 결정 사항

브레인스토밍에서 정한 것.

| 항목 | 결정 |
| --- | --- |
| 순번 편집 방식 | 행마다 ▲▼로 자리를 바꾸고, 저장 시 목록 위치대로 1..n을 다시 매긴다 |
| 글 추가 후보 | 시리즈와 같은 카테고리의 글. 초안 포함. 다른 시리즈 소속 글은 그 시리즈 이름을 표시하고 선택하면 옮겨온다 |
| 시리즈 삭제 | 소속 글이 하나라도 있으면 화면과 서버 양쪽에서 막는다. 글을 먼저 빼야 지울 수 있다 |
| 소속·순번 변경 API | 시리즈 단위 일괄 저장. 로컬에서 편집한 뒤 저장 한 번으로 트랜잭션 반영 |

## 설계

### 1. 라우팅과 내비게이션

| 경로 | 화면 |
| --- | --- |
| `/admin` | 비공개 글 관리 (기존) |
| `/admin/series` | 시리즈 목록 |
| `/admin/series/[id]` | 시리즈 상세. `id`는 시리즈 UUID |

세 페이지 모두 서버 컴포넌트가 껍데기이고, 내용은 클라이언트 컴포넌트가 그린다.
접근 제어는 기존 방식 그대로 클라이언트 게이트다. API는 서버에서 세션을 검사한다.

**`hooks/useAdminGate.ts`** — `AdminPostsManager`에 박힌 게이트 로직을 꺼낸다.
`{ canAccessAdmin, status }`를 돌려주고, 세션 로딩이 끝났는데 관리자가 아니면 홈으로 보낸다.
`AdminPostsManager`도 이 훅을 쓰도록 바꾼다.

**`components/Admin/AdminNav.tsx`** — 탭 두 개.

```ts
const ADMIN_TABS = [
  { href: '/admin', label: '비공개 글 관리' },
  { href: '/admin/series', label: '시리즈 관리' }
];
```

`current` prop으로 현재 탭을 받는다. 현재 탭은 검정 배경·흰 글자, 나머지는 테두리만.
`/admin/series/[id]`에서는 "시리즈 관리"가 현재 탭이다.

### 2. 시리즈 목록 (`/admin/series`)

**데이터**: 새 조회 API 없이 기존 두 쿼리를 쓴다.

- `['series']` → `getSeries()`: 시리즈 전체.
- `['posts', 'preview', 'all']` → `getAllPostsForPreview()`: 초안 포함 전체 글. 시리즈별 글 수를 여기서 센다.

**표**: 열은 제목, 카테고리, 글 수(초안 포함), 생성일. 제목은 상세로 가는 링크다.
정렬은 카테고리 순(dev, travel, talk, photo) 다음 제목 가나다순.

**행 동작**

- 편집: 기존 `SeriesModal`에 `series`를 넘겨 연다. 저장되면 모달이 `['series']`를 무효화한다.
  소속 글이 있으면 카테고리 선택을 잠근다. 카테고리가 바뀌면 글의 목차 링크와 시리즈 URL이 어긋나기 때문이다.
- 삭제: 글 수가 0일 때만 활성화. 확인 대화상자를 거쳐 `deleteSeries(id)`를 부르고 `['series']`를 무효화한다.
  글이 있으면 버튼을 비활성화하고 "글 N건. 먼저 빼야 삭제할 수 있습니다."를 보여준다.
  글 수를 아직 모르면(전체 글 조회 실패) 역시 비활성화하고 "글 수를 확인하지 못했습니다."를 보여준다.
  삭제가 서버에서 거부되면(409) 전체 글 조회를 다시 받아 글 수를 맞춘다.

**상단**: "새 시리즈" 버튼(`SeriesModal`). 시리즈가 없으면 빈 상태 안내.

컴포넌트: `components/Admin/AdminSeriesList.tsx`.

### 3. 시리즈 상세 (`/admin/series/[id]`)

**데이터**: 목록과 같은 두 쿼리에서 `id`에 해당하는 시리즈와 그 소속 글을 골라낸다.
조회가 실패하면 "시리즈 정보를 불러오지 못했습니다"와 다시 시도 버튼을 보여준다.
쿼리가 끝났는데 시리즈가 없으면 "시리즈를 찾을 수 없습니다"와 목록으로 가는 링크를 보여준다.

**머리**: 제목, 카테고리 칩, 설명, 편집 버튼(`SeriesModal`), 목록으로 링크.

**소속 글 목록**: 초기 순서는 공개 시리즈 페이지와 같은 규칙이다.
순번 오름차순, 순번 없는 글은 뒤로, 그 안에서는 게시일(초안은 저장일) 오름차순.

행마다: 위치 번호(1부터), 제목(에디터 `/editor?id=` 링크), 공개/비공개 뱃지, 게시일, ▲, ▼, 제거.
▲는 첫 행에서, ▼는 마지막 행에서 비활성화.

**도구 모음**: "글 추가", 변경 여부 표시("저장되지 않은 변경"), "되돌리기", "저장".
되돌리기와 저장은 변경이 없으면 비활성화. 저장 중에는 저장 버튼이 비활성화된다.

**로컬 상태**는 글 id의 순서 배열 하나다. ▲▼·추가·제거는 이 배열만 바꾼다.
기준선(마지막으로 저장되거나 불러온 배열)과 다르면 변경 상태다.

**저장**: 배열을 그대로 `PUT /api/series/posts?id=<시리즈 id>`에 보낸다.
성공하면 `['posts']` 접두 쿼리 전부와 `['series']`를 무효화하고 기준선을 저장한 배열로 바꾼다.
실패하면 서버 메시지를 `alert`로 보여주고 로컬 편집을 유지한다. 기존 화면들과 같은 방식이다.

**되돌리기**: 기준선으로 복원한다.

저장이 진행되는 동안에는 ▲▼·제거·글 추가를 막는다. 그 사이의 편집이 저장 후 동기화에 묻혀 사라지기 때문이다.
전체 글 목록에서 사라진 id(다른 곳에서 삭제된 글)는 화면·변경 판정·저장 본문에서 무시한다.

페이지를 떠나면 저장하지 않은 변경은 사라진다. 이탈 경고는 두지 않는다.

**글 추가 대화상자** (`components/Admin/SeriesPostPicker.tsx`):
후보는 시리즈와 같은 카테고리이면서 현재 로컬 목록에 없는 글. 게시일(초안은 저장일) 내림차순, 초안 포함.
행마다 제목, 공개/비공개 뱃지, 날짜, 다른 시리즈 소속이면 "다른 시리즈: 이름".
"추가"를 누르면 로컬 목록 맨 끝에 붙고 후보에서 사라진다. 대화상자는 닫히지 않아 여러 개를 이어서 넣을 수 있다.
후보가 없으면 "추가할 수 있는 글이 없습니다".

컴포넌트: `components/Admin/AdminSeriesDetail.tsx`.

### 4. 순수 로직 (`utils/seriesEditor.ts`)

화면에서 쓰는 목록 조작을 순수 함수로 분리한다. 전부 단위 테스트 대상이다.

| 함수 | 동작 |
| --- | --- |
| `sortSeriesPosts(posts)` | 초기 정렬. 순번 오름차순, 없는 글은 뒤로, 그 안에서 게시일(없으면 저장일) 오름차순 |
| `moveItem(ids, index, 'up' \| 'down')` | 새 배열을 돌려준다. 경계에서는 그대로 |
| `appendItem(ids, id)` | 끝에 붙인다. 이미 있으면 그대로 |
| `removeItem(ids, id)` | 뺀다. 없으면 그대로 |
| `isSameOrder(a, b)` | 순서까지 같은지 |

### 5. API

#### 새 엔드포인트: `PUT /api/series/posts?id=<시리즈 id>`

본문: `{ "postIds": ["…", "…"] }`. 배열 순서가 곧 순번이다. 빈 배열은 "전부 뺀다"는 뜻이다.

처리 순서:

1. 관리자 세션이 아니면 401. (`/api/series`의 다른 메서드와 같다.)
2. `id`가 없으면 400. UUID가 아니거나 시리즈가 없으면 404.
3. 본문 검증. 어긋나면 400과 이유.
   - `postIds`가 문자열 배열이어야 한다.
   - 각 항목이 UUID 형식이어야 한다 (`utils/isUuid`).
   - 중복이 없어야 한다.
   - 모든 글이 존재해야 한다.
   - 모든 글의 카테고리가 시리즈 카테고리와 같아야 한다.
4. Prisma 트랜잭션 하나로 반영한다.
   - 지금 이 시리즈에 속해 있지만 목록에 없는 글: `seriesId = null, seriesOrder = null`.
   - 목록의 글: `seriesId = 시리즈 id, seriesOrder = 위치(1부터)`.
   - 다른 시리즈에 있던 글은 이 갱신으로 자연히 옮겨진다.
5. 무효화. `revalidateContent`에 아래 위치를 넘긴다 (경로 중복은 헬퍼가 걸러낸다).
   - 이 시리즈: `{ category, seriesSlug }` → 홈, 카테고리, 시리즈 페이지.
   - 영향받은 글 전부(이전 소속 ∪ 새 목록): `{ category, slug }`.
   - 글을 빼앗긴 다른 시리즈: `{ category, seriesSlug }`.
   - 그 시리즈에 남은 글 전부: `{ category, slug }`. 목차와 이전/다음 편이 바뀌기 때문이다.
6. 응답 `200 { message, data: { seriesId, postIds } }`.

본문의 형식 검사(문자열 배열·UUID·중복)는 `lib/api/seriesPosts.ts`의 `parseSeriesPostIds(body)`로 분리해 단위 테스트한다.
존재 여부와 카테고리 검사는 DB 조회가 필요하므로 라우트 안에서 한다.
무효화 위치 계산도 같은 파일의 순수 함수로 분리해 테스트한다.

이 라우트는 Supabase 클라이언트 대신 Prisma를 쓴다. 여러 행을 원자적으로 바꿔야 하는데
Supabase REST에는 트랜잭션이 없기 때문이다. comments·thoughts 라우트에 선례가 있다.

#### 기존 `PUT /api/series` 보강

UUID가 아닌 id는 404. 카테고리를 바꾸려는데 소속 글이 있으면(초안 포함) 409로 거부한다.
글의 상세 URL이 `/카테고리/슬러그`라서 시리즈만 다른 카테고리로 옮기면 목차 링크가 전부 깨진다.

#### 기존 `DELETE /api/series` 보강

UUID가 아니거나 없는 시리즈는 404. 삭제 전에 소속 글 수를 센다(Prisma `post.count`, 초안 포함).
1건 이상이면 `409 { error: '소속 글이 있어 삭제할 수 없습니다. 글을 먼저 시리즈에서 빼세요.' }`.
화면에서 버튼을 막더라도 서버가 최종 방어선이다.

#### 클라이언트 API (`lib/api/series.ts`)

`updateSeriesPosts(seriesId, postIds)` 추가. 기존 `apiFetch` 관례를 따른다.

### 6. 감수하는 부작용

- 저장하면 소속 글 전체의 순번이 1..n으로 다시 매겨진다. 손으로 띄엄띄엄 넣은 번호는 유지되지 않는다. 의도한 동작이다.
- 글 수와 추가 후보를 클라이언트에서 전체 글 목록으로 계산한다. 글이 63건이라 문제없다.
  수천 건이 되면 서버 집계로 바꿔야 한다.
- 관리자 한 명이 쓰는 도구라 동시 편집은 다루지 않는다. 마지막 저장이 이긴다.

## 검증

- 단위(vitest): `seriesEditor`의 다섯 함수, `parseSeriesPostIds`, 무효화 위치 계산.
- `tsc --noEmit`, `next lint`, `next build`.
- 실제 흐름: 관리자 로그인이 필요하므로 로그인된 브라우저에서 확인한다.
  시리즈 만들기 → 상세에서 글 추가·이동·제거·저장 → 공개 시리즈 페이지에서 순서 확인
  → 글이 있는 시리즈 삭제 시도(차단) → 글을 모두 뺀 뒤 삭제.

## 범위 밖

- 드래그 앤 드롭 정렬.
- 여러 시리즈에 걸친 일괄 작업.
- 시리즈 대표 이미지.
- 글 삭제(글 관리는 에디터와 비공개 글 관리에서).
- 저장하지 않은 변경에 대한 이탈 경고.
- 서버 페이지네이션·집계.
