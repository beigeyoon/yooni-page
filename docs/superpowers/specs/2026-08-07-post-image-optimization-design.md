# 본문 이미지 최적화 설계

작성일: 2026-08-07
대상: yooni-page (https://yooni.seoul.kr)

## 배경

ISR 도입으로 HTML은 CDN에서 55ms에 도착하게 됐다(커밋 00a7ec0).
그런데 글 페이지의 체감 로딩은 여전히 느리다. 검증 중 Playwright의 `load` 이벤트가
타임아웃났고, 대기 중이던 요청 15건이 전부 Supabase 스토리지의 원본 사진이었다.

## 현재 상태

### 측정

발행된 글 59편의 본문에서 이미지 URL을 추출해 전수 측정했다.

| 항목 | 값 |
| --- | --- |
| 고유 본문 이미지 | 135개 (14개 글에 집중) |
| 총 용량 | 400 MB |
| 평균 / 중앙값 | 2.96 MB / 2.54 MB |
| 최대 | 13.67 MB |
| 2MB 초과 | 99개 |

이미지가 많은 글 상위: 치앙마이-새로운-여행-시작(25장), 치앙마이-올드시티에서의-4박-5일(23장),
신혼여행-톨레도(16장), 신혼여행-포르투-1(15장).

원본은 아이폰 카메라 그대로다. 표본 3장 모두 3024×4032(12.2MP) 또는 2352×1568이었고,
본문 컨테이너 폭은 `max-w-[780px]`이다. 즉 표시 폭의 3~4배 해상도를 그대로 내려보내고 있다.

### 왜 이게 문제인가

Supabase Free 플랜은 스토리지 1GB, 대역폭 5GB/월이다.
스토리지는 400MB로 이미 40%를 쓰고 있고, 대역폭은 치앙마이 글 한 편(25장 ≈ 74MB) 기준
**방문 67회면 월 한도가 소진된다.** 검색 유입을 늘리려는 목표와 정면으로 충돌한다.

### 원인

`next.config.ts`에는 이미지 최적화 설정이 이미 갖춰져 있다.
Supabase 호스트가 `remotePatterns`에 있고, `formats`는 webp/avif, `minimumCacheTTL`은 30일이다.

그런데 본문 이미지는 이 파이프라인을 타지 않는다.
`src/utils/optimizePostHtml.ts`는 `<img>` 태그에 `loading`·`decoding`·`fetchpriority`·`alt`만
채워 넣고 `src`는 원본 Supabase URL 그대로 둔다.
`next/image` 컴포넌트를 쓰는 곳(NavBar, 홈, PhotoSlide 등)만 최적화되고 있다.

## 목표

1. 방문자에게 가는 이미지 전송량을 한 자릿수 배수로 줄인다.
2. Supabase 대역폭 소비를 이미지당 월 1회 수준으로 낮춘다.
3. 원본을 보존한다.

## 설계

### 1. URL 변환 유틸 분리 — `src/utils/postImageSrc.ts` (신규)

Supabase 스토리지 URL을 Next.js 최적화 URL로 바꾸는 순수 함수를 둔다.

```
isOptimizableImageSrc(src)   → Supabase 스토리지 URL인지 판정
buildOptimizedSrc(src, w)    → /_next/image?url=…&w=…&q=75
buildSrcSet(src)             → 640w, 828w, 1080w 후보 문자열
```

`optimizePostHtml`이 이미 100줄에 가깝다. 이미지 URL 규칙까지 넣으면
"태그 속성 정규화"와 "이미지 출처 변환"이라는 두 가지 일을 하게 되므로 분리한다.

호스트는 하드코딩하지 않고 `NEXT_PUBLIC_SUPABASE_URL`에서 유도한다.
`next.config.ts`의 `remotePatterns`와 어긋나면 `/_next/image`가 400을 반환하는데,
한쪽만 바뀌는 상황을 막기 위해서다.

### 2. `optimizePostHtml` 확장

기존 속성 처리에 `src` 재작성과 `srcset`·`sizes` 추가를 얹는다.

렌더 순서가 `optimizePostHtml(sanitizePostHtml(post.content))`이므로
(`src/app/[category]/[slug]/page.tsx:362`) optimize가 나중이다.
따라서 새로 붙이는 `srcset`·`sizes`는 sanitize 허용 목록에 걸리지 않는다.
**이 순서가 뒤바뀌면 두 속성이 제거된다.**

### 3. 적용 범위와 파라미터

Supabase 스토리지 URL만 변환하고 `data:` URI와 외부 이미지는 그대로 둔다.
`remotePatterns`에 없는 호스트를 `/_next/image`에 넘기면 이미지가 깨지기 때문이다.

- 후보 폭: 640, 828, 1080 (`next.config.ts`의 `deviceSizes` 부분집합)
- 품질: `q=75` (Next.js 기본값)
- `sizes`: `(max-width: 780px) 100vw, 780px`

1080px을 상한으로 둔 이유는 아래 실측 때문이다. 1920px 후보를 포함하면
레티나 화면이 그것을 골라 998KB가 되어 절감이 4배로 줄어든다.
1080px 상한이면 레티나에서도 467KB이고 1.4배 밀도라 본문 사진으로는 충분하다.

이미지 그룹(`--count`)에서는 실제 표시 폭이 780px보다 작아 과다 다운로드가 생기지만,
그룹별 폭을 계산하는 복잡도에 비해 이득이 작아 감수한다.

### 4. 실측 근거

원본 4.22MB(3024×4032 JPEG)를 로컬 프로덕션 빌드의 `/_next/image`로 변환해 측정했다.

| 후보 폭 | AVIF | WebP | 원본 대비 |
| --- | --- | --- | --- |
| 640px | 197 KB | 196 KB | 4.5% |
| 828px | 300 KB | 311 KB | 6.9% |
| 1080px | 467 KB | 491 KB | 10.8% |
| 1920px | 998 KB | 1108 KB | 23.0% |

일반 화면은 828px 후보를 골라 약 300KB, 레티나는 1080px 후보로 약 467KB가 된다.
치앙마이 글 한 편이 74MB에서 8MB 안팎으로 줄어든다.

Supabase 대역폭은 Vercel이 원본을 한 번 가져와 30일 캐시하므로
135장 × 4.2MB ≈ 570MB/월이 상한이 되어 5GB 안에 들어온다.

### 5. 리스크

**Vercel Hobby의 이미지 최적화 한도를 넘으면 최적화가 실패해 이미지가 보이지 않을 수 있다.**
고유 이미지가 135개라 현재는 여유롭다고 보지만 이는 추정이며, 정책도 자주 바뀐다.
프로덕션 검증에서 실제 응답을 확인한다.

되돌리기는 쉽다. 원본 URL이 `url=` 파라미터에 그대로 남아 있고,
`optimizePostHtml`에서 변환 호출만 빼면 이전 동작으로 복귀한다.

## 검증

| 항목 | 방법 |
| --- | --- |
| 변환 정확성 | `postImageSrc` 순수 함수 단위 테스트 |
| 태그 조립 | `optimizePostHtml` 단위 테스트 (현재 테스트가 없어 함께 추가) |
| 실제 동작 | 로컬에서 변환된 URL이 200을 주고 바이트가 줄었는지 실측 |
| 회귀 | 404 매트릭스, 기존 44개 테스트, 스크린샷 |
| 프로덕션 | 글 페이지 전체 이미지 전송량 측정, 이미지 표시 확인 |

로컬 추론으로 끝내지 않는다. 직전 작업에서 로컬 TTFB로 프로덕션을 예측했다가 10~20배 빗나갔고,
이번에도 첫 추정(150~250KB)이 실측(300KB)과 어긋났다.

## 범위 밖

- **업로드 시 리사이즈와 기존 135장 마이그레이션** — 스토리지 400MB를 줄이려면 필요하다.
  지금은 전송량이 급한 문제이고, 스토리지는 1GB 중 40%라 여유가 있다.
  1GB에 가까워지면 별도 작업으로 다룬다.
- 이미지 그룹의 정확한 `sizes` 계산.

## 정정: CLS는 문제가 아니다 (2026-08-07 추가)

이 문서는 처음에 "본문 `<img>`에 `width`·`height`가 없어 레이아웃 이동이 남는다"고 적었다.
CSS를 확인하지 않고 일반론으로 단정한 것이었고, 사실이 아니다.

`src/app/globals.css:121`이 이미 공간을 예약한다.

```css
.image-album img {
  width: 100%;
  aspect-ratio: 1 / 1;
  object-fit: cover;
}
```

본문 이미지는 모두 `.image-album` 안에 들어가고 CSS가 종횡비를 고정하므로,
브라우저가 이미지 크기를 몰라도 자리를 먼저 확보한다.

프로덕션 실측(Playwright PerformanceObserver, 뷰포트 2종 × 페이지 4종 × 2회):

| 페이지 | 데스크톱 | 모바일 |
| --- | --- | --- |
| 글(16장) | 0.047 | 0.000 |
| 글(25장) | 0.015 | 0.004 |
| 홈 | 0.013 | 0.000 |
| 카테고리 | 0.000 | 0.000 |

Google의 "good" 기준 0.1의 절반 이하다.
첫 측정에서 모바일 글 하나가 1.831로 나왔으나 이후 5회 재측정에서 재현되지 않아 이상치로 본다.

**다만 `aspect-ratio: 1/1`은 세로 사진을 정사각형으로 잘라 보여준다는 뜻이다.**
앨범 스타일이 의도라면 그대로 두면 되고, 사진 전체를 보여주도록 바꾸면
종횡비 고정이 풀리면서 그때는 CLS가 실제로 발생한다.
그 시점에는 이미지별 크기 정보가 정말로 필요해진다.
